## Guidebook

From `openspec/specs/follow-up/spec.md`:

- Four counts, three lists by default
- The fourth list is reachable by selecting its card
- Selecting the selected card clears the filter
- Entry leads with elapsed time
- The section heading names its ordering above the card
- Every entry can open its conversation and be archived
- Empty section is explicit
- Unknown counts are not drawn as zero
- Closed entry leaves the section and its count
- The archived strip belongs to its section
- Badge totals the four sections

## Diagnosis

**Step 8 is a real defect, and I proved it was not my fixture.** The archive
button produced `400 FST_ERR_CTP_EMPTY_JSON_BODY`. The route
(`apps/api/src/return-reminders/routes.ts:175`) declares no 400 at all, so the
refusal came from Fastify before the handler. Called from the page with the
session token:

- with `Content-Type: application/json` and no body → **400**
- with no content-type header → **200**, and the return archived correctly

So the endpoint works and the client's request was malformed. The cause is
`send()` in `apps/web/src/api/returnReminders.ts`, which set
`content-type: application/json` unconditionally while passing
`body: undefined`. Its only two bodyless callers are `archiveVehicleReturn` and
`unarchiveVehicleReturn` — both entirely broken, on every return, for every
user. `cancelScheduledMessage` in `apps/web/src/api/scheduled.ts` already sends
`headers()` with no content-type, so the correct pattern was two files away.

The 200 I sent by hand while diagnosing is also what produced step 9's evidence
that the *rendering* side was never at fault: count, empty state, archived strip
and rail badge all updated correctly once the request was well formed.

**The session wall from `2026-09-10-conversas-inbox.md` recurred, on schedule.**
It reappeared roughly an hour after the previous storage clear, which makes it
reproducible and tied to the access token's one-hour lifetime rather than to
anything this screen does. Recorded as finding 2 with that added detail.

Re-driven live afterwards: step 9. |
| 2 | defect — fixed by change `session-recovery` | The SPA's session dies after about an hour and never recovers — every call 401s, the app retries without bound, and only clearing browser storage fixes it. `hydrateMvpSession` (`apps/web/src/AppProviders.tsx:104`) snapshots the token once at boot with no `onAuthStateChange`, and returns before its grant fallback. Observed twice, an hour apart. | **Fixed** by change `session-recovery` (`openspec/changes/session-recovery/`), which first specified it: the `auth` spec had no scenario for a good session starting to be refused, so a fix inside a testing change would have been inventing the requirement. Three parts. `AuthHydrate` now subscribes to `onAuthStateChange` and mirrors `TOKEN_REFRESHED`/`SIGNED_IN`/`SIGNED_OUT` into the store, so a token the client refreshes in the background is the one that gets sent. A 401 from `GET /auth/me` during hydration is read as a refused session rather than an unknown unit, and triggers `recoverSession()` — which nulls the bearer, clears the client's storage with `signOut({ scope: "local" })`, and re-grants — while `parse()` reports any mid-life 401 through a small `sessionRecovery.ts` registry that keeps the HTTP layer free of auth policy. And the TanStack Query `retry` is now `retryUnlessRefused`, so a refused token is never retried; that unbounded retry is what turned a dead session into the 401 storm rather than a merely stale screen. A loop guard makes a recovery whose OWN fresh token is refused terminal. **Pinned** by `apps/web/src/AppProviders.session-recovery.test.ts` (twelve cases that await `recoverSession()` directly, no mounting) and four mounted end-to-end cases in `apps/web/src/AuthHydrate.test.tsx`. **Still no tour asserts it**: tours start from a clean browser context, so the state needs either a wall-clock hour or a forged stored session — a unit concern, which is why the pin lives in Vitest. |
| 3 | none | Nothing else. Counts, lists, the card filter, the links back, the empty states and the archived strip all behaved as specified. | — |

### Update 2026-10-04 — Rumo Errado red, diagnosed from code and the scratch database

Not a screen defect. Retorno vencido is ordered most overdue first, and the demo
seed's Omie mock customer ("Maria Linked", return due 2026-07-15, no
conversation) sorts above E2E Turista. The tour's
`arquivarRetornoButtons(...).first()` therefore archived Maria's return: the
section count fell, but `Abrir conversa` links — which she does not have (spec
scenario "A return without a conversation has no Abrir conversa") — did not, and
the tour expected them to fall by one. Desinteressado counted the same links
against the card and was only green after Rumo Errado had archived Maria on that
database. The tour now archives its own customer's entry (`overdueEntryOf`) and
counts entries with `entryCount`. Both were checked on the rendered DOM of two
overdue customers, in headless Chromium, before the tour was changed.
