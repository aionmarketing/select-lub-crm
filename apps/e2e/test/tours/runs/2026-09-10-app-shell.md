## Diagnosis

**Two 5xx bursts during steps 3–6 were my fixture, not the app.** Walking to
Serviços logged two console errors, `500` on `GET /api/tags/apply-options`; the
API log named a `ZodError` in `toTagDto` (`apps/api/src/tags/prisma.ts:37`). The
task 5.2 seed I had just written set `Tag.color = "#F2C200"`, and
`tagColorSchema` is a closed enum of `primary|secondary|error|warning|info`.
The same shape repeated on `/relatorios` (`GET /api/tags`) and `/configuracoes`
(`GET /api/templates`), the latter from `toTemplateDto` because I had seeded
`allowedVariables = ["cliente","placa"]` against a closed enum of
`nome_cliente|placa`.

Both were fixed in `seed-e2e.ts` and the walk re-driven clean. The second fix
needed two attempts: the first only changed the `create` branch of the upsert,
so the already-written bad row survived re-seeding. That is recorded in the seed
as a comment, because it is the kind of thing that silently comes back.

**No app-originated console error and no HTTP 5xx** on the re-driven walk.

**Nothing left for Evolution.** The mock's log is empty for the whole run, which
is the guard working: the shell tour never sends, and could not have.

**Transcription caught a race the drive could not.** The first transcribed run
of Período Chuvoso failed: after activating Preto the primary button still read
`rgb(234,182,61)`. Not a defect — MUI transitions `background-color` over a few
hundred milliseconds, and the live drive had read the colour seconds after the
click (each MCP call is its own round trip) while the spec read it immediately.
Fixed in the spec with `expect.poll` rather than by weakening the assertion, and
the sample was pinned to the named `Nova conversa` button instead of "the first
button in `main`" so it cannot drift to another control. Worth stating plainly:
the interactive drive is *more* forgiving of timing than the spec it produces,
so a green drive does not guarantee a green transcription.

**And the first fix was not enough.** Running the whole tour suite together —
rather than this file alone — failed the same step again, this time capturing
`rgb(149,121,55)`: a *blend* of the yellow and black palettes, mid-transition.
Waiting for "a colour different from the previous one" is satisfied by a
half-finished transition, and the post-reload settled `rgb(48,48,48)` then did
not match it. The condition is now two consecutive equal reads that also differ
from the previous palette — stable *and* actually remapped. Worth recording
because the weaker fix passed this file in isolation twice; only the full-suite
run, under load, exposed it. A tour that is only ever run alone is not verified.

## Findings

| # | Kind | What | Where it went |
| --- | --- | --- | --- |
| 1 | none (defect) | No defect in the shell. All six routes render, `/login` redirects, and the palette behaves exactly as `design-system` specifies, including the fallback. | — |
| 2 | surprise | Tag colour and template variables are validated **on read**, not just on write. A single row outside the closed domain is representable in Postgres (`color String?`, `allowed_variables Json`) and takes the whole list endpoint to `500` — blanking Configurações and disabling the Relatórios tag filter — instead of being skipped or reported. Today the only writer is the API, which validates on write, so this is defence-in-depth rather than a live defect. | Not a defect against any current scenario, so nothing pinned. Raised for the spec owner in this change's `Findings` roll-up; out of this change's scope to change behaviour. |
| 3 | surprise | The garbage-palette fallback does not heal the stored value: after falling back, `localStorage` still holds the invalid id, so every boot re-does the fallback. The spec says only that it falls back, which it does. | Recorded here; no scenario to pin against. |
| 4 | tooling | The MCP drives a **headed** Chromium, which requests `/favicon.ico`; the repo has no `apps/web/public`, so every page logs a 404 console error. Playwright's own headless run never requests it, which is why neither the default suite nor the worked-example tour saw it. | Not an app defect and not in the tour fixture's allow-list, because the transcribed tours run headless where it does not occur. Noted so a future headed drive is not surprised. |
